# Verify webhooks

A payment processor posts signed notices to a tiny HTTP service. The service
accepts a notice only when its HMAC signature verifies, and the check is
generated by the compiler from one `actor` declaration rather than written by
hand. The service then signs data of its own, a receipt, with the `Crypto`
capability, and shows how to verify it.

## The idea

A webhook is authenticated by a signature over the raw request body: the sender
computes an HMAC of the bytes with a shared secret, and you recompute and
compare it. Doing that by hand is easy to get wrong. You might re-serialise the
parsed body and hash different bytes, compare with `==` and leak timing, or
forget the check on one route.

In Bynk you declare the sender as a `Signature` actor and name it in the
handler's `by` clause. The boundary then reads the body once, recomputes
HMAC-SHA256 over those exact bytes, compares in constant time and answers `401`
before your handler runs. Only then is the body parsed, from the same bytes.
The route can't forget the check, because the actor is part of its signature.

When the data is your own, there is no sender to declare, so you sign and verify
with `bynk.crypto` yourself. It is experimental, so `bynk.toml` opts in with
`[unstable] allow = ["bynk.crypto"]`.

## Walkthrough

1. **`src/payments/hooks.bynk`** is the whole service. The actor is the
   webhook check:

   ```bynk
   actor Processor {
   	auth = Signature(
   		secret = "WEBHOOK_SECRET",
   		header = "X-Signature",
   		timestamp = "X-Timestamp",
   		tolerance = 300
   	)
   }
   ```

   The handler names it, and does nothing about signatures itself:

   ```bynk
   	on POST("/webhooks/payment") (
   		body: Payment
   	) -> Effect[HttpResult[String]] by Processor given Crypto, Secrets {
   ```

   The receipt is our own signed data, so it calls `Crypto` directly. A
   context function can declare `given`, just as a handler does:

   ```bynk
   fn receiptFor(paymentId: String) -> Effect[Option[String]] given Crypto, Secrets {
   	let key <- Secrets.get("RECEIPT_KEY")
   	match key {
   		None => Effect.pure(None),
   		Some(k) => {
   			let mac <- Crypto.hmac(Sha256, Bytes.fromUtf8(k), Bytes.fromUtf8(paymentId))
   			Effect.pure(Some(mac.toHex()))
   		},
   	}
   }
   ```

   `verifyReceipt` checks one with `Crypto.verifyHmac`, which compares in
   constant time. Never compare MACs with `==`.

2. **`tests/payments/webhooks.bynk`** runs as `system`, so the real generated
   check sees each request. The driver signs calls as `Processor` declares,
   and the reserved principals send what it must refuse: no signature
   (`by Nobody`), a signature made with the wrong secret (`by Forged`) and an
   old timestamp (`by Stale`):

   ```bynk
   		let r <- webhooks.POST("/webhooks/payment", notice) by Forged
   		expect r is Rejected(Unauthorized)
   ```

   A signed but malformed body is refused too. A valid signature never skips
   validation.

3. **`tests/payments/receipts.bynk`** runs at the `unit` tier with the real
   cryptography. It checks that the webhook's receipt verifies, that it fails
   for a different payment and for input that isn't hex, and that nothing is
   signed without a key.

## Run it

```sh
bynk test .
```

To serve it locally, give it both secrets:

```sh
bynk dev -- --var WEBHOOK_SECRET:dev-secret --var RECEIPT_KEY:dev-key
```

An unsigned `curl` gets `401`. To send a signed one, sign `<timestamp>.<body>`:

```sh
BODY='{"id":"pay_1","amountPence":1250}'
TS=$(date +%s)
SIG=$(printf '%s.%s' "$TS" "$BODY" | openssl dgst -sha256 -hmac dev-secret -hex | sed 's/.*= //')
curl -X POST localhost:8787/webhooks/payment -H 'content-type: application/json' \
  -H "X-Timestamp: $TS" -H "X-Signature: sha256=$SIG" -d "$BODY"
```

It answers with the receipt, as a hex string. Change one character of `BODY`
after signing and it answers `401`.
